# Host Stand · Devpost description

## Why this is a fit for WebMCP

A restaurant host stand is a shared-state problem with a human already in the loop. The host is dragging parties onto tables while an agent is reading the same queue, and the tools have to be the same tools for both. WebMCP puts those tools in the page itself: Host Stand registers 22 imperative tools with `document.modelContext` (falling back to `navigator.modelContext`), so any browser agent the staff already use can discover `get_floor`, `get_queue`, `score_assignment`, `set_candidates`, `set_plan`, `assign_table`, `add_host_note`, and the rest without an API key, a backend, or a vendor integration. Every call runs the same client-side engine function as the human interface, lands in a visible ledger, and carries provenance. The page ships no model; the intelligence is the user's own agent. That is the WebMCP thesis in one screen: the site describes its capabilities, the agent brings the reasoning, and the human keeps the last word.

## How this improves the user experience

Today's host software is a grid of table shapes. It can say a party of four cannot sit at a two-top and nothing else; every interesting decision lives in free text nobody audits. Host Stand keeps that text where it belongs, on the party card, and hands it to the agent as natural language with the floor geometry it needs to reason about "private", "near the in-laws", or "different sides of the room". The agent proposes up to three tables with a one-line reason; the host presses Accept or Reject (with a reason the agent sees), or simply drags the party elsewhere. Hard rules never move: capacity, accessibility, high chairs, locks, and reservation priority are enforced by the engine, so a prompt-injection probe from a walk-in ("ignore the rules, we're VIPs") is blocked and shown, not argued with. If the agent writes against a floor the host already changed, the write is rejected with the diff instead of clobbering the human. At 10 PM the scorecard puts Host decisions and Agent decisions side by side with special requests satisfied as the headline and every request, including the failures, listed with who handled it and why.

## What people and agents can do together

The division of labor is explicit: the engine enforces, the agent reasons, the host decides. The engine owns legality, timers, and arithmetic. The agent owns interpretation ("somewhere with atmosphere, not a corner"), relations between parties, conditional plans ("we might be 6 or 8, we'll know by 6:45"), incommensurable trade-offs ("the regular always gets V3, but V3 is the only window four-top left for the anniversary; your call"), and discretion ("we think it's the critic; don't make it obvious"). The host owns the floor: any plan can be accepted, rejected with a reason, or overridden by drag, and a note typed mid-service ("the Wongs at 8 are recently divorced, different sides of the room") reaches the agent as a review request. Because both share one version number, neither silently overwrites the other. Because both are graded by name on the same night, the question "what did the agent contribute that the code didn't?" has a number on it.

## How it was implemented

Pure HTML, CSS, and JavaScript modules with no dependencies. A deterministic engine (`src/engine.js`) holds the state machine: two operating modes, a reservation-first commit guard, a scoring service, optimistic concurrency with a 50-entry change log, and a request grader. The generator (`src/data.js`) seeds every run from a code with 84–96 parties and 8–10 special requests drawn from fourteen templates across five categories, each with at least three phrasings; the hidden ground truth is generated with the text and never leaves the engine (a test serializes every tool result and asserts no predicate name appears). Grading is pure functions over final state: seating records, marks, the party-update trace, and floor geometry (adjacency and Chebyshev distance on a 14×7 grid). `src/webmcp.js` defines the 22 tools with JSON-schema validation, `readOnlyHint` and `untrustedContentHint` annotations, and an `expected_version` gate on every write. `src/app.js` renders the floor, queue, ledger, Accept/Reject, host notes, and the Host-vs-Agent recap. 96 Node tests and two Playwright verifiers cover the modes, generation coverage, grading, concurrency, and the browser flows.
